The listing does not establish current phone/IVR or SMS booking. [Official app listing](https://play.google.com/store/apps/details?id=com.hyderabadwater.hmwssb) | **CHANGE** project wording: app is confirmed; IVR/SMS are proposed access channels, not verified HMWSSB channels. | BHASHINI | The official portal offers language services including speech-to-text, text-to-speech, translation, and language detection; production API access requires organization registration. [BHASHINI](https://bhashini.gov.in/) | **ADD** as an option to evaluate for accessibility; keep fixed reviewed UI translations. Do not depend on its availability for the offline demo. |
| Urdu wording | Research found no reliable Hyderabad-specific Urdu UI wording source or native review. | **OPEN**; get a native Urdu reviewer before shipping strings. |
| Font licences | Not audited. Self-hosting supports offline use but does not itself establish redistribution rights. | **OPEN**; select a font only after checking its license and Telugu/Urdu rendering, including Urdu line spacing. |
| TRAI SMS rules | TRAI's official guidance says bulk senders (including government bodies) must register as Principal Entity, register a header, register content templates, and transmit IDs. [TRAI sender guidance](https://www.trai.gov.in/advice-to-senders), [government entities](https://trai.gov.in/government-entities) | **KEEP** outbound-SMS-only project assumption; production sender would need an authorized entity/provider and registration. Template rules do not prove that inbound SMS is impossible. |
| Telugu/Urdu SMS length | Exact gateway behavior and encoding-dependent segment limits were not established from primary sources in this research. | **OPEN**; keep messages concise, test with chosen provider and scripts, and show multipart status/cost before production. |
| Hindi share | No sufficiently reliable Hyderabad-specific language-share source verified. | **KEEP** Hindi as an inclusion choice, not a population-share claim. |
| Font / text size / targets | The cited source in the initial note was secondary. WCAG 2.2 AA target-size minimum is generally 24 by 24 CSS px with exceptions; WCAG 2.1 AAA is 44 by 44 CSS px. [WCAG 2.2 target size](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum), [WCAG 2.1 target size](https://www.w3.org/WAI/WCAG21/Understanding/target-size). The project's 48 px target is a stricter usability choice; 16 px body text is also a project floor, not a WCAG minimum. | **KEEP** 48 px targets and 16 px minimum text as product requirements; correct the standards attribution in the earlier table. |
| International comparators | No international utility was investigated deeply enough to support a design decision. | **DEFER**; not required to decide the P4 UI direction. |

## 5. Recommended updates to the solution document

1. In F14, distinguish JalLekha's proposed channels from verified HMWSSB channels. HMWSSB's app listing confirms app-based booking/status and Telugu/English; current IVR, inbound SMS, and operational APIs remain unverified.
2. Keep four JalLekha UI languages as a product decision. IndicConformer supports many Indian languages, including Telugu, Hindi, and Urdu; English voice-note transcription should not be promised without testing. Unsupported or low-confidence audio should remain available for human handling.
3. Treat SMS as outbound fixed templates for the demo. For production bulk messaging, plan sender/header/template registration with a telecom provider. Do not state that inbound SMS is categorically unavailable.
4. Add GIGW 3.0 checks to the design review, and keep the 48 px touch-target and 16 px text requirements as stricter project choices rather than quoting them as WCAG minima.
5. Before production, get native review of Urdu strings, verify font redistribution rights and rendering, and test message encoding/segments with the selected SMS provider.

Research is complete for the time-boxed pass. The open items above are concrete product/production follow-ups; they do not block review of this note.
