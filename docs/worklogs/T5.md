# `feat/t5-notices` — `T5`

- **Owner / date:** P3, 2026-10-02.
- **Purpose:** Build F15: an officer enters an HMWSSB supply-interruption notice; its areas are matched to wards; it becomes an A5 outage; both are logged; residents can be alerted in their language.
- **What we found:** `docs/research/P3.md` F15 decided "Keep officer entry": notices are press releases with area lists and hours, there is no machine-readable feed, and D14 has not been fetched, so no parser was built. A5's `create_outage` returns `entity_type` / `entity_id` outside its payload and puts `reason` (free text) in it; T5 passes the code `hmwssb_supply_notice` and copies the entity fields into the payload for `ledger_store.record`. A5 needs `people_affected`, which a notice does not state. P1's tables give 221 sections (142 placed on a 2016 ward) and 145 wards, with no locality alias table; "Uppal" is both Ward 10's name and a section P1 placed in Ward 7, so name matching must flag ambiguity. A 0.9 similarity threshold would have accepted the typo "Nacharm" (0.93) automatically, so the proposal is exact matches only.
