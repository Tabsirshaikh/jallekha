# `feat/t3-delivery` — `T3`

- **Owner / date:** P3, 2026-10-02.
- **Purpose:** Build F12 delivery proof: OTP to a registered representative, server-side geofence, a resident check by SMS, and the four outcomes (Confirmed / Disputed / Unconfirmed / Failed), each written to the ledger.
- **What we found:** S3's `otp.py` and `geofence.py` cover code derivation, hashing, expiry and distance, but not attempt counting or an OTP validity period (S3 review D10). `otp.derive_code` reads `otp_digits` from `config/trust.py`, so the 6-digit proposal is set there. Geofence at exactly 150 m is decided by floating-point error (S3 review D6, P2's file), so that one test is skipped and pending. The S3 ledger does not hash `entity_type` (D1); T3 keeps `entity_type` and `entity_id` in the payload so they are hashed. The solution document does not say what "mostly" means with ties or zero replies, or how long residents may reply.
- **What we changed:** `config/trust.py`: OTP decision (a) values and delivery-proof values; OPEN ones are marked "OPEN, owner to confirm". `services/ledger.py`: seven T3 event types in `EVENT_TYPES` only (two separate commits). New `services/delivery.py` (pure flow and outcome), `services/ledger_port.py` (`LedgerPort` + `InMemoryLedger` on the S3 chain), `services/sms.py` (template-key messages, fake provider). OTP tries from outside the geofence never use an attempt and never check the code; they are logged up to `outside_tries_max` (OPEN, 10) per visit, then one `outside_tries_exceeded` entry, then nothing. Models `representative`, `delivery`, `resident_response`, `delivery_outcome`. Tests `backend/tests/services/test_delivery.py`, `backend/tests/test_delivery_models.py`.
- **Validation:** Tests written first; the import failed before the service existed. 40 new tests pass, 1 skipped (exact 150 m, pending D6). `python tasks.py test` exit 0: 202 backend passed, 1 skipped, 1 frontend test, all P1 verifiers. `python tasks.py lint` exit 0. All data in tests is synthetic (made-up ids, phone numbers and a Hyderabad stop point); no real data used. Follow-up after PR #26 merged: `main` (S3-FIX #25, E2-FIX #24) merged into the branch, `python tasks.py setup` rerun (`pdfplumber`), exact-150 m test enabled and passing (D6 fixed); `python tasks.py test` exit 0: 239 backend passed, 0 skipped; lint exit 0. Then S3 review fixes handled in T3 (one commit each, tests first): D11 digit count stored and passed when re-deriving; D7/D9 bad coordinates or radius give `invalid_location`, never an unhandled error; D8 no inf / NaN in results or ledger; `seq` / `prev_hash` change `entry_hash`. `git grep compute_hash -- backend scripts`: no matches. `python tasks.py test` exit 0: 257 backend passed, 0 skipped; lint exit 0.
- **Known limitations:** Decisions (a) OTP digits / validity / attempts and (b) ties / zero replies / reply window are **OPEN, owner to confirm**, and so is `outside_tries_max = 10`; the implemented values are proposals. The geofence position comes from the driver's phone and can be faked, so it is one of two checks, together with the resident replies. One yes with the rest silent gives a majority (silence counts for nothing), which the owner should confirm. No API routes (T10), no database-backed ledger (T6), no real SMS provider; the OTP key is passed in by the caller. Message wording per language is not written here (template keys only).
