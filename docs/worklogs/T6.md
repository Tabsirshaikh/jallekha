# `feat/t6-ledger` — `T6`

- **Owner / date:** P3, 2026-10-02.
- **Purpose:** Wire the F18 ledger: store entries in the database, one concurrency-safe `record()` call for every module, chain verification with the first broken entry and reason, key ids for rotation and a daily published head hash. Tamper-evident, not blockchain.
- **What we found:** S3-FIX (#25) already hashes every `LedgerEntry` field (`entry_hash`) and rejects NaN / Infinity; `compute_hash` no longer exists. `LedgerEntry` has no `key_id` field, so T6 puts `key_id` inside the payload (hashed) and in a column, without changing P2's file. A plain chain cannot show that the newest entries were removed, or that the key holder rebuilt the chain (S3 review D2); the research note (`docs/research/P3.md` F18, Crosby & Wallach 2009) answers this with a daily head hash published outside the system. The research note decides key ids and daily publication, not the rotation period, the day boundary or the publish time. A concurrency probe with one try per append showed real sequence collisions between two writers on SQLite, so the retry matters.
- **What we changed:** `config/trust.py` and `.env.example` (`LEDGER_KEY_ID`, `LEDGER_OLD_HMAC_KEYS`, OPEN values); `services/ledger.py` `EVENT_TYPES` only (one separate commit: notice, outage, contest, contest reply, field check); models `ledger_entry`, `ledger_head`; `services/ledger_store.py` (`StoredLedger`, `record`, `verify_chain`, `ChainCheck`, `publish_head`); `services/ledger_port.py` (`InMemoryLedger` is now the stored ledger on in-memory SQLite); `routers/ledger.py` + `main.py` (read-only list and verify); `scripts/trust/publish_ledger_head.py`; tests `backend/tests/services/test_ledger_store.py`, `backend/tests/test_ledger_router.py`.
- **Validation:** Tests written first. 37 new tests pass: tamper cases for every stored field, gap, reorder, wrong / missing key, concurrent appends, truncation and rewrite caught by the published head, key rotation, endpoints, publish script. T3's test files are unchanged against `main` and pass on the stored ledger. `python tasks.py test` exit 0: 308 backend passed, 1 frontend test, all P1 verifiers. `python tasks.py lint` exit 0. Test data is synthetic (made-up ids and keys); no real data used.
- **Known limitations:** OPEN, owner to confirm: key rotation period (`ledger_key_rotation_days = 90`, not enforced), head-hash day boundary (`ledger_head_utc_offset_minutes = 330`) and publish time (`ledger_head_publish_time_local = "06:00"`). Entries after the last published head are only as safe as the database until the next head goes out; the head protects only if it is published outside the system (channel: P4 / T5). No cron schedule is built. Concurrency was tested on SQLite; PostgreSQL relies on the same unique `seq` and retry.
- **Handoff / next step:** Other modules write with `app.services.ledger_store.record(entry_type, payload, actor)` (payload: `entity_type`, `entity_id`, ids and numbers only). P2 (plans, overrides, weights, debt) and T5 / T7 use the event types listed in `EVENT_TYPES`. P4 / T5: show the published head on the ward report card / SMS. T10: `GET /ledger/entries`, `GET /ledger/verify` exist. Owner: decide the OPEN values.
