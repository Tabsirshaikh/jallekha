# E6 — coverage-map GeoJSON

Branch `feat/e6-coverage`, based on `feat/e5-underserved` with the reviewed E4 artifacts merged because E6 depends on both E4 and E5.

## Findings

- The reviewed GHMC source contains 145 polygons with stable OSM relation identifiers.
- E2 contains 134 provisional number-only Census links and 11 rows without usable WAD values, but zero location-validated assignments. The WAD values can be displayed only as historical, provisional evidence.
- E4 has exact HMWSSB section totals and concentration metrics. It has no verified section-to-ward transfer or section population denominator, so ward bookings and bookings per 1,000 must remain null.
- E5 places all 145 wards in `DATA_REVIEW_REQUIRED`, with zero eligible areas and zero field-check candidates. An unavailable candidate is not the same as `false` or zero.
- No verified public-tap location and service dataset supports a claim about people living within 500 metres of a working tap.

## Implementation

- `backend/app/services/coverage.py` creates three independent GeoJSON `FeatureCollection` views while copying the reviewed polygon geometry exactly.
- `water_access_evidence.geojson` exposes 134 historical WAD shares with an explicit location-review status; 11 missing values remain null and every polygon is ineligible for operational allocation.
- `booking_coverage.geojson` preserves all ward booking values as null. Exact section-level E4 facts appear only as collection metadata and are not transferred to polygons.
- `field_check_status.geojson` exposes E5 review states and reason codes while preserving null booking values and null field-check decisions.
- `layers.json` provides the three-layer contract, per-layer non-null counts, operational-use restriction, and the explicit exclusion of the unsupported 500 m public-tap layer.
- `build_coverage.py`, `verify_coverage.py`, output hashes, tests, and the `P1:E6` workflow make the package reproducible and reject identifier drift.

## Validation and limits

The E6 artifacts are map-ready views of reviewed evidence status, not measurements of current water need or proof of under-service. They must not drive allocation until upstream location and booking-transfer gates pass. A UI must render null as unavailable, visually distinguish provisional evidence from validated values, and retain the layer-level interpretation text.

Automated checks assert exactly three 145-feature layers, unchanged geometry, 134 provisional WAD values, zero invented ward booking metrics, zero invented field-check decisions, deterministic output hashes, and exclusion of the unsupported public-tap layer.

## Handoff

Consumers should read `data/derived/coverage/layers.json` before loading a layer and use each feature's `display_status`, `value_basis`, and `allocation_eligible` fields. Do not calculate ward booking coverage from the section table unless a reviewed crosswalk and population denominator are added in a later task.
